# 修复报告里的 fix commit，真的在受审代码里吗？

**一个可复用的核查方法 —— 以及为什么"8/14"这个数字才是有意思的部分。**

> English version: `MR_FIX_COMMIT_CHECK.md`

---

## 一句话

修复报告通常写着「已在 commit `<sha>` 中修复」。在做 **mitigation review**（或把某条 finding 当作"已关闭"）之前，你可以**机械地、每个报告约两分钟**查一遍：

1. **抽取** —— 从 remediation 文档里取出声称的 fix commit。
2. **比对** —— `GET /repos/{owner}/{repo}/compare/{fix_sha}...{reviewed_sha}`
   → `status: ahead` **且** `behind_by: 0` ⇒ 该修复**是受审版本的祖先** ⇒ **在**。
3. **区分** —— 对解析不到的：`GET /repos/{owner}/{repo}/commits/{fix_sha}`
   → `200` = 提交存在，但不在受审版本的线上；
   → `422/404` = **不在该仓库里**。

**重点不是那 8 条通过的，是那 6 条没通过的** —— 以及**分清"修复不在"和"我的提取坏了"**。

> **脚本（Step 1–3 一条命令）：**
> `check_fix_commits.sh <owner/repo> <受审版本sha> <remediation.pdf|txt>`
> 直接打印下面的 triage 表；`--dry` 只抽 SHA，不打 API。

---

## 为什么值得做

mitigation review 只问一个问题：**这次修复是否真的关掉了那条 finding？**

**所有人都去读 diff，极少有人先查管道：**

- 声称的 fix commit，**到底在不在我正在审的这份代码里**？
- 如果不在 —— 是因为项目**在别处修了**（另一个仓库、另一个分支），还是因为**这条修复根本没进这个版本**？

如果 commit 不在受审版本里，那么**读多少 diff 都无法判断那条 finding 是否关闭**。
这个缺口，值得在你把预算花在"确实存在的部分"之前先补上。

---

## Step 1 —— 抽出声称的 fix commit

Remediation 的 PDF 通常由文本生成（不是扫描件），所以 `pdftotext` 拿到的是**文字层** —— SHA 就是作者敲进去的，不是 OCR 猜的。这是好事。

```bash
pdftotext -q remediation.pdf remediation.txt
grep -oE '\b[0-9a-f]{40}\b' remediation.txt | sort -u
```

**保留「finding ↔ SHA」的对应关系**，一张小表就够。

## Step 2 —— 这个修复是不是受审版本的祖先？

GitHub 的 compare 端点直接、便宜地回答这个问题：

```bash
PIN=<受审版本 sha>
curl -s "https://api.github.com/repos/$OWNER/$REPO/compare/$FIX...$PIN" \
  | python3 -c 'import json,sys;d=json.load(sys.stdin);print(d.get("status"),d.get("ahead_by"),d.get("behind_by"))'
```

| `status` | `behind_by` | 含义 |
|---|---|---|
| `ahead` | `0` | ✅ 受审版本**包含**该修复（`ahead_by` = 两者之间差几个提交） |
| `identical` | `0` | ✅ 同一提交 |
| `behind` | `>0` | 🔴 受审版本**早于**该修复 ⇒ **未包含** |
| `diverged` | — | ⚠️ 历史分叉 ⇒ 人工看 |
| `404` | — | ⚠️ 该路径下无共同祖先 ⇒ 转 Step 3 |

> 直线历史时这一步是平凡的。注意：`compare/A...B` 在**两提交沿该路径无共同祖先**时会返回 **404** —— 这就是 Step 3 存在的原因。

## Step 3 —— 分清"没修"和"你无法判断"

对每一条解析不成功的：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  "https://api.github.com/repos/$OWNER/$REPO/commits/$FIX"
```

- `200` ⇒ 提交**确实存在**于该仓库，只是不在受审版本的祖先链上（被 **rebase / squash** 掉了，或在一条从未合并的分支上）。
- `422` / `404` ⇒ **不在该仓库**。此时有三种可能，**绝不许把它们悄悄合并成一句结论**：
  1. 修复在**另一个仓库**（跨链 / 多仓项目很常见）；
  2. 提交在**私有**仓库里（或该仓库后来转私）；
  3. 文档里的 SHA **本来就写错了**。

**在得出任何结论之前，先看该组织的公开仓库列表。** 多组件的项目常常是"一个组件公开、其余私有"。

## Step 4 —— 别骗自己：提取噪声 vs. 真 SHA

在你写下"修复不见了"之前，先排除**是你自己的提取把哈希弄坏了**：

- `pdftotext` 读的是**文字层**。如果文档是扫描件，你什么也拿不到 —— 那时你在 OCR 十六进制，会坏字符（`…0e3c` → `…0e3cv`）。**优先选有文字层的文档**；用 `pdftotext … -` 输出到终端肉眼扫一眼有没有乱码。
- **强对照**：同一个 SHA 字符串**同时出现在两份独立产生的文档**里（例如两家不同审计机构的 remediation 报告）？独立作者不会把同一串 40 位随机十六进制**错成一样**。那是一条真实的提交引用。
- 弱对照："看起来像十六进制"。**任何被弄坏的字符串也可以看起来像十六进制。**

## 公开样例

> **项目细节**已刻意隐去 —— 只报结果的**形状**。
> 下文不指向任何具体项目；那组数字是**模式的示例**，不是对某个团队的披露。

取一个「此前审计的 remediation 报告已公开」的项目，按上述步骤跑 **14 条声称的 fix commit**：

- **8 条** → `status: ahead`、`behind_by: 0` ⇒ **在受审版本中** ✅
- **6 条** → 在该仓库中**解析不到**。
  - 其中**两条同时出现在两份各自独立产生的 remediation 文档**里 ⇒ **不是**提取噪声。
  - 该组织的公开仓库都解析不到 ⇒ 最可能在**另一个（可能私有的）仓库**，或被 rebase 的分支上。

此处**中性措辞很重要**：**这不是漏洞声明。** 它只是关于"从受审版本出发能验证什么"的陈述。**那 6 条可能修得好好的 —— 只是修在你看不到的地方。**

## 这个方法**不能**证明什么

把边界写清楚，因为这个检查最典型的失败方式就是**过度断言**：

- **present ≠ correct**。祖先提交只说明修复**落进来了**，**完全不说明**它是否真的关掉了那条 finding。后者仍需读 diff，并且 —— 在可行时 —— **复现原始现象以证明它不再发生**。
- **rebase 会毁掉信号**。被 squash 的主线会让原始 SHA 解析不到，**但改动其实在**。
- **私有仓库不可见**。所以 `404`/`422` 是**"待人工核查"的旗标**，**永远不是**"未修复"的结论。
- **`ahead_by` 不是质量指标** —— 它只是提交距离。

所以这个检查的诚实产物是一张 **triage 表**：

| 结果 | 你可以说的话 |
|---|---|
| 在（`ahead`,`behind_by=0`） | "修复在受审版本里 —— 现在去验它是否奏效" |
| 能解析但不是祖先 | "修复存在，但不在这个版本里 —— 去问为什么" |
| 解析不到 | "**从这里无法验证** —— 去问是哪个仓库/分支" |

---

## 收束

mitigation review 的本质是**验证声明**，而其中最便宜可验的一条 —— "fix commit 在这个版本里" —— 却通常被当作理所当然。

**两分钟的管道检查，把一份报告变成一张 triage 清单；把"我读过 diff"变成"我查过这些修复到底在不在"。**
